## The one thing today is for

> **Does thalamic stim measurably move the cortical MAV feature?**
> `|corr| u -> y > 0.1`

Everything else — the model, the observer, the closed loop — is downstream of
that number. If it comes back below 0.1, no amount of fitting produces a real
model, only a confident-looking one. **Get to this number early.** It is Phase C
and you should reach it within the first hour of having tissue.

# PHASE B — First live capture

## B-setup. Decide two numbers before you touch anything

**1. `-UMax`, the stim amplitude ceiling.**
This is the **pulse-amplitude envelope** — one pulse amplitude per 100 Hz control
point, the same quantity recorded in the acute stimblock CSVs (values ±{7, 12,
20, 30, 40}, where 40 is the physical ceiling). It is a real charge/compliance
limit, **not** an arbitrary clamp. Nothing in this code knows anything about
tissue safety.

> Start well below the ceiling. `-UMax 10` is a reasonable first value if you
> have no better information for this preparation. Raise it only after a short
> run at a lower value has shown the preparation tolerates it.

**2. `-Channels`, which stim pair(s) move.**
New today: excitation used to drive **all 16 channels simultaneously**, which is
both a lot of simultaneous current and a 16-input MIMO fit from a single record.
`-Channels 3` holds every other channel at `uMin` (0 = nothing delivered).

- **First capture: ONE pair.** It makes the go/no-go unambiguous — if `|corr|`
  is high, you know exactly what caused it. The fitter auto-selects only
  channels that moved, so nothing downstream needs configuring.
- **Later, for the real MIMO model:** `-Channels (1..16)`, longer record.
- Pick the pair from the acute catalog if you have a prior on which pairs drove
  the strongest cortical response; otherwise start with a mid-array pair.

1. Is the TDT circuit running and the PO8e actually collecting?

### → B5. `numChannels` is not what you expected (**check this one carefully**)
The loop is started with a channel count (`16` by default in `2_loop.ps1`). From
the acute-dataset work: **touch blocks stream both arrays — cortical S1 is Wav1
channels 1–16, thalamic VPL is 17–32.** If the PO8e is streaming 32 channels and
you tell the loop 16, you get the first 16, which may or may not be the array you
want.
- Confirm the printed `Streaming. numChannels=N` against what the circuit sends.
- If it streams 32 and you want cortex, verify cortex is the **first** 16 in this
  circuit's channel order before trusting it. Getting this backwards means you
  spend the day identifying stim→thalamus instead of stim→cortex.
- `2_loop.ps1 -InputChannels 32` if you need all 32 (the parameter is
  `-InputChannels`; `-Channels` is a STIM parameter on 1_server/1c_server) — but
  then the feature vector is 32 long and `feature_map` in `mpc_test.m` matters
  correspondingly more.

### → B6. `replies=0`, `timeouts` = every tick
The two processes are not talking.
1. Is the server in terminal 2 still showing `ready` (not crashed, not exited)?
2. Ports must match: both sides use 31000 (request) / 31001 (reply).
3. Windows Firewall on a loopback UDP port — unusual, but if a prompt appeared
   and was dismissed, allow it.
4. The server auto-stops 1 s after a bounded run finishes. If you restarted the
   loop without restarting the server, the server is gone. Restart terminal 2.

### → B7. Loop is healthy but no stim reaches the RZ2
The loop reports success because UDP is fire-and-forget — a healthy summary is
**not** evidence that stim was delivered.
1. Confirm you did not pass `-Sim` (which sets `--skip-udp-send`).
2. Confirm `-RZ2` is the right IP; check the `UDP socket connected to RZ target:`
   line.
3. **Verify at the TDT end, not here.** The `sSig` store records delivered stim
   as ground truth — that is the authoritative check that current actually went
   out, and it is worth doing once early rather than discovering at analysis time
   that the whole day recorded zeros.
4. **Isolate the stim path with a known envelope** (added 2026-08-05). No PO8e,
   no MATLAB, no controller, no model — just a commanded envelope on the wire:

   .\rig\5_envelope.ps1 -Preview                                # draw it, send nothing
   .\rig\5_envelope.ps1 -RZ2 10.1.0.100 -Channels 3 -UMax 10    # record in Synapse first
   ..\PythonIntanAnalysis\.venv\Scripts\python.exe rig\check_envelope.py `
       --sent envelope_sent_saw.csv --block <block_dir> --plot envelope_check.png

   A slow sawtooth gives corr > 0.95 on a working path, plus the command→`sSig`
   units conversion and the true transport lag. Do this **before** interpreting
   any `|corr| u→y` result: it separates "stim never came out" from "stim came
   out and the tissue did not respond", which no other check on this list does.

# PHASE C — GO/NO-GO (the decision the day turns on)

```powershell
.\rig\3_fit.ps1 -Run 1 -Sweep
```

Fits every output channel and prints one line each. Takes ~1–2 min for 16
channels.

```
   ch     |corr|   bestStim   valFit%   order   slowestPole   verdict
  ----    -------   --------   -------   -----   -----------   --------
     7      0.626          3     68.51       6        0.9253   RESPONDS
```

`|corr|` is peak absolute cross-correlation over lags 0–500 ms, on the same
causal alignment and warm-up discard the fitter uses.

**Verified tonight in both directions:** on a real capture with no causal
relationship it reports 0.006–0.010 and `NO CHANNEL RESPONDED`; on a synthetic
capture with a planted order-2 plant (poles 0.9/0.7, SNR 3) it finds the right
channel at `|corr| 0.626`, valFit 68.5%, recovered pole 0.9253. It neither
hallucinates nor misses.

## The decision

| best `\|corr\|` | meaning | do |
|---|---|---|
| **> 0.3** | strong, unambiguous | → Phase D |
| **0.1 – 0.3** | real but modest | → Phase D, but take the second capture first |
| **0.05 – 0.1** | marginal | → C2 |
| **< 0.05** | nothing | → C1 |
| **> 0.9** | *too good* — suspect artifact | → **C4** |

### → C1. No channel responded (`|corr| < 0.05`)
Work through these in order; they are ordered by likelihood × cheapness.

1. **Was stim actually delivered?** Check `sSig` at the TDT end (B7). This is
   the most common cause and the cheapest to rule out. A whole day can be spent
   diagnosing a "non-responsive preparation" that never received current.
2. **Amplitude too low.** `-UMax 10` is deliberately conservative. If the
   preparation tolerates it, re-run at a higher `-UMax` (within your safe limit).
   This is the highest-yield knob.
3. **Wrong pair.** You drove one pair. Try 2–3 other pairs — the acute work found
   electrode repositioning strongly shifts which channel responds, and the
   effective rank of the stim→response operator is only ~3 of ≤15 pairs, so pairs
   are genuinely not interchangeable.
   Fast version: `-Channels (1..16)` for one 60 s run. If *nothing* responds with
   all pairs driven, the problem is not pair selection.
4. **Wrong array / wrong 16 channels.** See B5.
5. **The MAV feature is insensitive.** The evoked response is a focal negative
   LFP at ~15–28 ms. MAV over the tick window may be averaging it away. This is
   not fixable from PowerShell today — note it and move on.
6. **Record too short.** 60 s at `clockTicks=5` should be plenty. If you ran
   shorter, extend to `-Ticks 12000`.

**C1-exit (time-box):** if three attempts across amplitude and pair selection all
return `|corr| < 0.05`, **stop trying to close the loop today.** Bank two clean
open-loop captures at the highest safe amplitude, save everything (Phase F), and
treat the negative result as the day's finding. It is a real and reportable one:
it constrains the biomimetic story directly.

### → C2. Marginal (0.05–0.1)
Cheapest fixes, in order: longer record (`-Ticks 12000`) → SNR improves with
√time; then higher `-UMax`; then `clockTicks 3` if you suspect the response is
faster than the excitation band (0.04–10 Hz at `clockTicks=5`).
**Do not fit and save a model off a marginal capture.** Get it above 0.1 first.

### → C3. Many channels respond
Normal and fine — a thalamic stim pair drives a cortical neighbourhood. Take the
strongest for the first model. Note the spatial pattern; it is exactly the
per-block individuality the acute analysis characterised, and worth recording in
the notebook.

### → C4. `|corr| > 0.9` — treat as suspect, not as success
A near-perfect correlation between a stim command and a neural feature at these
amplitudes is more likely **stim artifact leaking into the MAV window** than a
neural response. The feature is a mean-absolute-value over the tick window, and
the artifact is by far the largest thing in that window if it is not blanked.
Check:
- Does `|corr|` peak at **lag 0**? A real cortical response peaks at ~15–28 ms
  (1–3 ticks). A zero-lag peak is the artifact.
- Is the "response" present on *every* channel about equally? Artifact is global;
  a real response is focal.
- Is blanking active in the TDT circuit?

A model fitted to artifact will close the loop beautifully and control nothing
real. This is the most dangerous single failure mode of the day, because every
number looks excellent.

## C5. Take the second capture regardless

```powershell
# terminal 2
.\rig\1_server.ps1 -Run 2 -UMax 10 -Channels 3 -Ticks 6000 -Kind multilevel -Seed 777
# terminal 1
.\rig\2_loop.ps1 -Run 2 -RZ2 <IP>
```

`-Kind multilevel` visits interior amplitudes, so it also tests amplitude

than one validated on 30% of run 1 — and the acute analysis found a real
nonlinearity (MLP adds 0.06–0.19 condition-R² on every well-powered block), so
this is not a formality.

# PHASE D — Fit and validate

## D-1. Full report on the winning channel

```powershell
.\rig\3_fit.ps1 -Run 1 -Channel 7
```

Read in this order:
1. **`|corr|`** — already decided in Phase C.
2. **`valFit%`** on held-out data. Should be meaningfully above 0.
3. **Chosen order.** ARX is equation-error and buys apparent fit with extra
   states; `parsimonyTolerance` takes the smallest order within 1.0 pp of the
   best. On a synthetic order-2 plant it picks 4–6. **Do not read the order as
   the physical state count.**
4. **Time constant.** Sanity-check against the evoked response you know. The
   acute data puts the peak at 15–28 ms. A model reporting a 5 ms or 5 s time
   constant is wrong.

## D-2. Cross-record validation — **do this before saving**

```powershell
.\rig\3_fit.ps1 -Run 1 -Channel 7 -Validate 2
```

Fits on run 1, free-runs the model against run 2. Reports three numbers and a
verdict. Verified tonight on synthetic records: `ok` for the real channel
(68.5% in-record → 65.8% cross-record), `no-model` for a noise channel.

### → D2-fail. `did NOT transfer`
The model describes run-1-specific structure. Causes, in order: the preparation
changed between runs (drift, anaesthetic depth); the excitation was too short;
the response is nonlinear enough that a linear model is record-specific.
**Do not deploy it.** Either re-fit on a longer single record, or accept an
open-loop day.

### → D3. `dynamics transferred, but the OPERATING POINT MOVED`
Baseline drift between records. The dynamics are real and usable; the DC offset
is not. This is recoverable — it mostly matters because the MPC will see a bias
it cannot reject. Proceed to closed loop, but expect a steady-state offset and
do not chase it as a controller bug.

### → D4. Unstable model / pole outside the unit circle
The fitter reports `all poles inside unit circle`. If not, do not save it — an
unstable plant model inside the MPC will produce confident nonsense. Re-fit with
a lower order: `fit_sysid_from_capture(file, struct('useOutputs',7,'orders',1:4))`.

### → D5. Chosen order is 8 (the top of the sweep)
The order sweep hit its ceiling, so the best order may be higher. Extend it:
`struct('useOutputs',7,'orders',1:12)`. But be suspicious — a high order on
neural data usually means noise colouring, not plant states.

## D-6. Save

```powershell
.\rig\3_fit.ps1 -Run 1 -Channel 7 -Save
```

Backs up `AllModels.mat`, writes the model as a plain struct into
`AllModels(10).sys`. (`0_preflight.ps1` also took a dated copy this morning.)

## D-7. **Set `feature_map` in `mpc_test.m`** ← easy to forget, breaks everything

measurement. **If the channel you identified is not channel 1, edit it now.**
Otherwise the MPC controls a channel it has no model of, and Phase E will look
like a controller problem when it is a wiring problem.

# PHASE E — Closed loop

> **First time this has ever closed on a real plant.** Before 2026-07-23 the
> observer gain was silently `zeros(...)` (the `place()` fallback, Control System
> Toolbox not installed) and the MPC ignored its measurement entirely. The fix —
> a toolbox-free steady-state Kalman gain — has only been tested on the toy
> first-order model. Keep a hand on Ctrl+C.

## E-1. Pick a reachable target
Take it from the **observed feature range** in the capture (`output N: range
[a b]` in the fit report). A target outside that range is unreachable, the
command pins at a bound, and the run tells you nothing. Aim for something the
feature actually visited — mid-range is a good first choice.

## E-2. Run

```powershell
# terminal 2
.\rig\4_mpc_server.ps1 -Target 250 -Ticks 3000
# terminal 1
.\rig\2_loop.ps1 -Run mpc1 -RZ2 <IP> -Ticks 3000
```

`4_mpc_server.ps1` calls `mpc_test([])` first to reset persistent state and pick
up the newly saved model, then reports at the end whether `out0` actually varied.

## What to watch, live

- **`out0` must change with `feature0`.** This is the whole test.
- `zeroTicks` in the loop summary — each is a tick that commanded zero because
  no fresh reply arrived.
- Saturation at 0 or `uMax`.

### → E1. `out0` is constant while `feature0` moves — **the loop is open**
This is the exact signature of the pre-2026-07-23 defect. In order:
1. **`feature_map` (D-7).** Most likely cause now. If the MPC is reading channel
   1 and the model describes channel 7, the measurement it gets is unrelated to
   the model and the observer correction does nothing useful.
2. **Did the observer initialise?** The fix now fails *loudly* — check terminal 2
   for a `warning` saying the controller will run open-loop. If you see it, the
   Kalman iteration did not converge on this model, which is new information
   (the toy model converged). A lower-order model (D4) is the quickest response.
3. **Is the target reachable?** An unreachable target pins the command, which
   looks like a constant. → E2.
4. **Did `AllModels` reload?** `4_mpc_server.ps1` calls `mpc_test([])`, but if you
   saved the model from a *different* MATLAB session than the server is running,
   confirm the file on disk is the one you think.

### → E2. Command pinned at 0 or `uMax`
The target is unreachable, or the model's DC gain is wrong.
- Move `-Target` toward the middle of the observed feature range.
- Check the fit's reported DC gain — if it implies the full `[0, uMax]` command
  range moves the feature by less than the distance to your target, no controller
  can get there. That is a plant fact, not a tuning problem, and it is itself a
  result worth writing down.

### → E3. Oscillation or instability
Stop the run. In order of what to try:
- **Lower the target** — you may be at the edge of the reachable set.
- **`qScale` in `mpc_test.m`** (default `1e-2`) is the process/measurement noise
  ratio and the knob for observer aggressiveness. It is a guess, never tuned on
  real data. Lower it to make the observer trust its model more and the
  measurement less.
- Remember the **structural 10 ms command lag** on the localhost path — it is
  modelled (`inputDelayTicks = 1`) but it does bound achievable bandwidth. A
  controller demanding faster response than 10 ms can deliver will ring.

### → E4. Many `zeroTicks` / high `timeouts` throughout (not just startup)
Expect ~15–25 zero ticks at startup while MATLAB warms — harmless (zero output =
no stim). Sustained zeros mean replies are not arriving fresh.
- Check server turnaround in terminal 2. Should be ~1–3 ms avg. If it is ~15 ms,
  the 1 ms timer-resolution object did not start — restart the server.
- Raise `-TimeoutMs` on `2_loop.ps1` from 5 to 8. The freshness thresholds
  themselves (100 ms / 250 ms) are loose and would need a C++ rebuild to change.

> **Do not attempt the deferred C++ changes today** (tightening
> `LOCALHOST_FRESH_OUTPUT_US`, accepting the newest reply instead of the exact
> in-flight sequence). They are worth doing, but not between an animal and a
> deadline. The binary you have is the one that was benchmarked.
