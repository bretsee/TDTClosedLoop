## Why

All five 2026-08-14 crashes are `0xc0000374` STATUS_HEAP_CORRUPTION in ntdll (identical
fault offset `0x112165`), on BOTH the jul23 and aug14 builds — found in the Windows
Application event log (Event ID 1000). Consequences:

- Build regression is ruled out; the fault is in a heap write somewhere in the process.
- It is an SEH fault: the C++ catch blocks never run → no `Summary:`, unflushed CSV, and
  **`zero_stim_outputs()` never fires — stim stays live after every crash** until zeroed.
- Prime suspect: `std::vector<int16_t> temp(nCh)` (cpp:1280) handed raw to
  `PO8e::readBlock((short*)temp.data(), 1, offsets)` (cpp:1319/1379). Runs 1 and 3 died
  right after huge card offset jumps (`Skipping ...`).

10 identical runs, fully instrumented, so each crash produces a full dump + a per-tick
trace, and each clean run banks saline timing data at uMax 30.

## ROOT CAUSE FOUND AND FIXED (runs c01–c03, same evening)

- **c01, c02** (normal runs): both crashed `0xC0000374` within ~5 packets; dumps show the
  identical signature — **16 consecutive float32 values written across two adjacent 32-byte
  LFH blocks**, corrupting the second block's header; detected later at
  `clamp_amplitudes_f32`'s per-tick allocation.
- **c03** (full PageHeap, diagnostic run): caught the corrupter red-handed —
  `0xC0000005` write fault **inside `PO8eStreaming.dll`** (`mov dword ptr [rcx],eax`),
  called from `Po8eSampleSource::readBlock`, guard page hit **exactly 32 bytes past
  `temp`'s buffer start**.
- **Root cause:** `PO8e.h` requires readBlock buffers of
  `nSamples * numChannels() * dataSampleSize()` bytes. The code hard-coded int16
  (2 bytes/sample) and never called `dataSampleSize()`. **The stream is float32
  (4 bytes/sample)** — 16 ch × 4 B = 64 B written into a 32 B buffer, on EVERY read.
  The spilled values are 0.5–3 mV — volts-scale data, confirming float32.
- **Second consequence (worse than the crash):** every "feature" read since the stream
  became float32 was reinterpreted garbage bytes (e.g. float 0.00118's high half-word
  0x3A9B = 14,987 as int16 — exactly the magnitudes seen on 08-14). All feature-based
  results from float32-era captures are invalid. The intermittency was allocation-order
  luck in whether the 32-byte spill hit a checked neighbor block.
- **Fix (rebuilt 2026-08-15 20:18, archived `aug15-fix.{exe,pdb}`):**
  `ISampleSource::sampleSizeBytes()` (PO8e → `dataSampleSize()`, sim → 2); raw byte
  buffer sized per the contract; frames decoded to float (int16 cast or float32 memcpy);
  ring now stores decoded floats; hard abort on unrecognized sample sizes. Sim-verified
  identical to pre-fix behavior on int16.
- **On hardware the banner now prints `sampleBytes=4 (float32)` — that line is the
  root-cause confirmation.** Features become volts-scale (~1e-3), which changes nothing
  in correlation-based analyses but invalidates any absolute-scale assumption.

**Runs c04–c10 are fix-verification + saline timing** (same checklist below). Prior
expectation ~2/3 crash rate; 7 consecutive clean runs ⇒ P≈0.0005 under the old rate.

8. **If CLEAN:** stop the recording normally; Terminal A should print `Wrote N capture rows`.
9. Note the startup `Discarded N frame(s)` backlog count in the ledger notes (suspected covariate).
10. Terminal A's MATLAB server is single-shot — restart it with the next label.

## Decision rules

- **Dump lands + WinDbg localizes the corruption** → decide mid-session: fix (`temp`
  headroom + frame-width validation) and use remaining runs to verify, or keep collecting.
  Collect **≥2 dumps** before fixing — with heap corruption the detector (an alloc/free
  elsewhere) is often far from the corrupter.
- **≥8/10 clean** (P≈0.003 under yesterday's ~2/3 crash rate) → the rate collapsed:
  heisenbug or an environmental covariate changed. Ship the defensive fix regardless.
- **Event 1000 but no dump** → stop; debug WER before burning more runs (should be
  impossible after today's crashtest verification).
